# ข้อกำหนด Proposed: ตรวจร่าง IRAC และแก้เมื่อมีหลักฐานรองรับ

รุ่นเอกสาร: 0.2 — 1 ตุลาคม 2026

สถานะ: มี prompt verifier/corrector, ตัวรัน และการตรวจ offline แล้ว ดู [รายงานสร้าง prompt](PROPOSED_PROMPTS.md) และ [คู่มือตัวรัน](PROPOSED_RUNNER.md) ยังไม่มีผลคำตอบ Proposed จาก Qwen จริง และยังไม่ตรึงค่าของ final test

เอกสารหลักที่ใช้ร่วมกัน: [แผนการทดลอง](RESEARCH_PROTOCOL.md) และ [รายละเอียด IRAC baseline](IRAC.md)

## 1. เป้าหมายและขอบเขต

ชื่อวิธีสำหรับรายงาน: **Prompt-based IRAC Verification and Conditional Correction**

คำถามวิจัย: เมื่อใช้โมเดลและบริบทกฎหมายเดิม การตรวจร่างตาม IRAC พร้อม feedback ที่ระบุหลักฐาน ช่วยหรือทำร้ายคุณภาพคำตอบจาก IRAC baseline ในกรณีใด และใช้ต้นทุนเพิ่มเท่าไร?

ลำดับทำงาน: ร่าง IRAC เดิม → ตรวจหนึ่งครั้ง → เก็บร่างเดิมหรือแก้หนึ่งครั้ง → จบ

- ใช้ Qwen2.5-7B น้ำหนักและ quantization เดียวกันสำหรับร่าง ผู้ตรวจ และผู้แก้ แยกบทบาทด้วยคำสั่งในแต่ละการเรียก
- ทดลองทั้ง Golden และ Saved Retrieved ภายในขอบเขต 4 วิธี × 2 context เดิม
- ตรวจร่างหลังสร้างเสร็จ ไม่ตรวจแทรกระหว่างการสร้างเหตุผลทีละขั้น
- ผู้ตรวจของเราเป็นโมเดลตัวเดิม จึงไม่ใช่ผู้ตรวจอิสระ และยังอาจให้ feedback ผิดได้
- ผล PASS/FAIL/UNCERTAIN ใช้เลือกขั้นตอนทำงาน ไม่ใช่คะแนน benchmark และไม่ใช่คำรับรองความถูกต้องทางกฎหมาย
- การตรวจทั่วไปที่ไม่มีเกณฑ์ IRAC เป็นข้อเสนอการทดลองเสริม ยังไม่เพิ่มเป็นเงื่อนไขบังคับ หากจะทำต้องบันทึกขอบเขตก่อน heldout

## 2. ที่มาจากงานวิจัยและส่วนที่เราดัดแปลง

| งานและตำแหน่งอ้างอิง | สิ่งที่ต้นฉบับรองรับ | สิ่งที่เรานำมาใช้ | ขอบเขตการกล่าวอ้าง |
|---|---|---|---|
| [Legal Prompting — Yu et al., §4.5 และ Figure 5](https://arxiv.org/html/2212.01326#S4.SS5) | ทดลองคำสั่งตามโครงสร้างกฎหมาย รวม IRAC แบบ zero-shot ในงาน COLIEE | ใช้ร่าง I/R/A/C และแปลงหน้าที่ของแต่ละส่วนเป็นเกณฑ์ตรวจ | rubric ผู้ตรวจในเอกสารนี้เป็นการดัดแปลงของเรา งานเดิมไม่ได้ให้ checklist นี้ และไม่ได้พิสูจน์ว่า IRAC ดีที่สุดทุกกรณี |
| [LegalReasoner, §4.2 และ §5.1.4](https://arxiv.org/html/2506.07443) | ใช้ process verifier ที่ฝึกเฉพาะ ตรวจ reasoning ทีละขั้นและแก้ตามประเภทปัญหา | ตรวจ ระบุปัญหา และให้คำแนะนำแก้ที่สัมพันธ์กับปัญหา | เราตรวจหลังร่างเสร็จ ไม่มี fine-tuned verifier หรือชุดเครื่องมือแก้ของต้นฉบับ จึงไม่อ้างว่า reproduce LegalReasoner |
| [Self-Refine — Madaan et al., §2 และ §3.1](https://arxiv.org/html/2303.17651) | โมเดลตัวเดิมสร้างร่าง ให้ feedback ที่เฉพาะเจาะจงและนำไปแก้ได้ แล้วปรับคำตอบ | แยกการตรวจและแก้เป็นคนละการเรียก ใช้ feedback ที่บอกตำแหน่งปัญหาและวิธีแก้ | ต้นฉบับใช้ few-shot prompts และทดลองหลายรอบ เราเริ่มโดยไม่มีตัวอย่างใน prompt และแก้ได้ครั้งเดียว |
| [Chain of Logic, §3](https://arxiv.org/html/2402.10400) | แยกองค์ประกอบของกฎและพิจารณาความสัมพันธ์ทางตรรกะก่อนรวมผล | ตรวจเงื่อนไข ข้อยกเว้น และความสัมพันธ์ เช่น “และ/หรือ” ใน R/A เมื่อกฎนั้นมีจริงใน context | ไม่บังคับสร้างนิพจน์ตรรกะทุกข้อ ไม่เพิ่ม one-shot example และไม่อ้างว่าใช้วิธี Chain of Logic เต็มชุด |
| [Huang et al., §6](https://arxiv.org/html/2310.01798) | self-correction อาจทำให้ reasoning แย่ลง และต้องพิจารณา feedback กับต้นทุนการเรียกโมเดล | ใช้คำสั่งตรวจเป็นกลาง เก็บก่อน–หลังและผลเสียจากการแก้ รายงานต้นทุน | ไม่สมมติว่า verifier ถูก หรือว่าการใช้โมเดลหลายรอบช่วยเสมอ |
| [NitiBench, §3.3.2 และการอภิปรายผล NitiBench-Tax ใน §5](https://arxiv.org/html/2502.10868) | ประเมิน Coverage, Contradiction และ citation แยกกัน การอ้างมาตราได้ดีไม่รับประกันการปรับใช้ถูก | ตรวจความเชื่อมโยงกฎกับข้อเท็จจริง และประเมินคำตอบด้วยคะแนนเดิมภายหลัง | ไม่สร้างคะแนนคุณภาพคำตอบใหม่จาก verdict ของ verifier |

ข้อกำหนด PASS/FAIL/UNCERTAIN, รูปแบบ JSON, การตรวจข้อความอ้างอิง, การเก็บร่างเมื่อขั้นตอนล้มเหลว, งบ tokens และการจำกัดหนึ่งรอบ เป็นการออกแบบของโปรเจกต์นี้ ต้องตรวจบน engineering ก่อนตรึง ไม่ใช่ข้อกำหนดที่คัดจาก paper

## 3. ข้อมูลที่แต่ละขั้นได้รับ

### 3.1 ใช้ร่างจาก IRAC baseline

- ใช้ผล engineering แบบครบชุดของ IRAC ไม่เลือกคำตอบจาก diagnostic หรือเลือกครั้งที่ตอบดีที่สุด
- จับคู่ด้วย `source_idx` และชนิด context เก็บ `runtime_idx` ประกอบ ไม่จับคู่ด้วยตำแหน่งแถวหรือจำนวนผลที่มี
- ร่างที่โมเดลเห็นใช้ `model_content` เดิมซึ่งมี `analysis`, `answer`, `citation_ids` ไม่ย้อนเดา P-ID จาก law/section ที่แปลงแล้ว
- ตรวจ question, context node IDs, ลำดับ, ข้อความ, provision map และที่มาของร่างก่อนเริ่ม หากจับคู่ไม่ได้ให้หยุดรายการนั้นเพื่อตรวจข้อมูล ไม่เรียกโมเดลแก้ความผิดพลาดในการจับคู่
- ถ้าไม่มีร่างสมบูรณ์เพราะ generation failure ให้บันทึก `draft_failed` ไม่สร้างร่างใหม่ ไม่ใช้ข้อความ JSON ที่ถูกตัดเป็นร่าง และไม่ลบข้อออกจากจำนวนที่ต้องรายงาน
- ข้อมูล provenance ย้อนหลังที่ไม่ได้บันทึก เช่น model digest ณ วันสร้างร่าง ต้องระบุว่าไม่ทราบ ห้ามนำ digest ปัจจุบันไปอ้างว่ารับรองอดีต เก็บข้อจำกัดนี้สำหรับ engineering และตรึง provenance ให้ครบก่อน final test

### 3.2 ข้อมูลนำเข้าของ verifier/corrector

| ข้อมูล | Verifier | Corrector |
|---|---|---|
| คำถาม | คำถามเดิม | คำถามเดิม |
| บริบทกฎหมาย | ข้อความทั้งหมดและลำดับเดียวกับร่าง IRAC | เหมือน verifier |
| ID ที่อนุญาต | P-ID และการจับคู่เดิม | P-ID และการจับคู่เดิม |
| ร่าง | `analysis`, `answer`, `citation_ids` เดิม | ร่างเดียวกัน |
| Feedback | ไม่มี | ผลตรวจที่ผ่านการตรวจรูปแบบและข้อความอ้างอิง |
| เฉลย/คะแนน/ชื่อวิธีอื่น | ไม่ได้รับ | ไม่ได้รับ |

Golden ใช้กฎหมายที่ exact resolver เดิมเลือกจาก `relevant_laws` ส่วน Saved Retrieved ใช้ Top 10 เดิม ไม่ค้นเพิ่ม ไม่ rerank และไม่เพิ่ม gold laws ให้ผู้ตรวจในฝั่ง Retrieved

การสร้างข้อความนำเข้าต้องเลือกรายการที่อนุญาตข้างต้นอย่างชัดเจน ห้ามส่งทั้งแถว CSV หรือทั้ง response record เพราะอาจมี `reference_answer`, `relevant_laws` หรือ metadata เฉลยติดไปด้วย คำตอบร่างของโมเดลเป็นข้อมูลที่อนุญาต ต่างจากคอลัมน์เฉลย `answer` ใน dataset

## 4. เกณฑ์ตรวจ I/R/A/C

ตรวจทั้ง `analysis` และ `answer` ของร่าง ไม่ตัดสินจากการมีตัวอักษร I/R/A/C ครบหรือจากการเลือก citation อยู่ใน enum เพียงอย่างเดียว

| แกน | คำถามที่ผู้ตรวจต้องตอบ | ตัวอย่างเหตุให้ FAIL | กรณีที่ควรระบุ UNCERTAIN |
|---|---|---|---|
| I — ประเด็น | ร่างตอบคำถามที่โจทย์ถามครบและตรงหรือไม่? | ข้ามคำถามย่อยที่ระบุชัด หรือเปลี่ยนบุคคล/ช่วงเวลาจนเป็นคนละประเด็น | โจทย์กำกวมจนไม่ทราบว่าถามกรณีใดแน่ |
| R — กฎ | ข้อความกฎและ citation รองรับด้วย context โดยรักษาเงื่อนไขและข้อยกเว้นหรือไม่? | อ้างว่ากฎอนุญาตโดยไม่มีเงื่อนไข ทั้งที่ข้อความที่อ้างกำหนดเงื่อนไขชัดเจน | ไม่มีข้อความเพียงพอให้ยืนยันกฎที่จำเป็น ไม่ควรเดากฎหมายจากความจำ |
| A — การปรับใช้ | ข้อเท็จจริงในโจทย์เข้าเงื่อนไขของกฎตามที่ร่างอ้างจริงหรือไม่? | ร่างบอกว่าเข้าเงื่อนไขทั้งสอง ทั้งที่โจทย์ระบุว่าไม่เข้าเงื่อนไขหนึ่ง หรือเพิ่มข้อเท็จจริงที่โจทย์ไม่ให้ | โจทย์ไม่ระบุข้อเท็จจริงสำคัญและไม่มีหลักฐานตัดสินเงื่อนไขนั้น |
| C — ข้อสรุป | คำตอบสุดท้ายตามจากกฎและการปรับใช้ และตอบประเด็นที่ถามหรือไม่? | analysis สรุปว่าไม่เข้าเงื่อนไข แต่ answer กลับให้สิทธิโดยไม่มีเหตุผลรองรับความต่าง | กฎหรือข้อเท็จจริงยังไม่พอให้ยืนยันข้อสรุป |

กติกาที่ใช้ร่วมกัน:

1. `PASS` หมายถึงไม่พบปัญหาสาระสำคัญตามเกณฑ์และหลักฐานที่มี ไม่ได้หมายถึงผ่านคะแนน benchmark
2. `FAIL` ต้องระบุข้อผิดพลาดที่มีผลต่อประเด็น กฎ การปรับใช้ ข้อสรุป หรือการรองรับข้ออ้าง พร้อมหลักฐานและคำแนะนำแก้ ไม่สั่งแก้เพียงเพราะสามารถเขียนให้สวยขึ้น
3. `UNCERTAIN` ใช้เมื่อยังตัดสินไม่ได้ ไม่แปลงความไม่แน่ใจเป็น FAIL เพื่อให้มีงานแก้ และไม่แปลงเป็น PASS เพื่อให้รายงานดูดี
4. ตรวจเฉพาะเงื่อนไขที่เกี่ยวกับคำถาม ไม่บังคับอธิบายกฎหมายทุกมาตราใน Top 10 หรือเพิ่มเงื่อนไขทางกฎหมายเอง
5. หาก context ไม่พอ ห้ามสรุปว่า “ไม่พบกฎหมายใน context = ไม่มีกฎหมายเช่นนั้น” การขาดหลักฐานอาจทำให้ตัดสินไม่ได้ หากพบการอ้างเกินหลักฐานที่ชี้ได้ชัด จึงระบุ FAIL และแนะนำลดความเด็ดขาดโดยไม่เติมข้อเท็จจริง
6. เหตุผลเดิมของแต่ละแกนต้องสอดคล้องกับ verdict เช่น ถ้าพบประเด็นที่ยังประเมินไม่ได้ในแกนนั้น ไม่บันทึก PASS ทั้งแกน
7. ภาษา analysis หรือเครื่องหมายหัวข้อที่ต่างจากคำสั่งเป็นข้อสังเกตแยก ไม่ใช่เหตุให้ตรวจแก้สาระเพียงอย่างเดียว
8. คำสั่งผู้ตรวจต้องเป็นกลาง: ร่างอาจถูก ผิด หรือมีหลักฐานไม่พอ ไม่เริ่มด้วยสมมติฐานว่า “คำตอบนี้ผิด จงหาข้อผิดพลาด”

## 5. รูปแบบ feedback ที่จะใช้สร้าง schema

ผลตรวจเป็น JSON อีกชุดหนึ่ง แยกจาก schema คำตอบเดิม มี top-level key เดียวคือ `checks` และมีรายการ I, R, A, C อย่างละหนึ่งรายการตามลำดับ ห้ามผู้ตรวจสร้างคะแนน Coverage/F1 หรือคำตอบฉบับแก้ในผลตรวจนี้

| ฟิลด์ | ข้อกำหนด |
|---|---|
| `axis` | `I`, `R`, `A` หรือ `C` |
| `verdict` | `PASS`, `FAIL` หรือ `UNCERTAIN` |
| `reason` | เหตุผลสั้นและเฉพาะกับร่าง/หลักฐานนี้ ต้องไม่ว่าง |
| `issues` | ถ้า FAIL ต้องมีอย่างน้อยหนึ่งปัญหา ถ้า PASS/UNCERTAIN เป็น `[]` |
| `issues[].draft_field` | `analysis` หรือ `answer` ที่เกิดปัญหา |
| `issues[].draft_quote` | ข้อความสั้นที่คัดตรงจาก field นั้น; ใช้ `null` ได้เฉพาะปัญหาการละประเด็นที่ไม่มีข้อความให้คัด และต้องระบุใน `problem` ว่าขาดอะไร |
| `issues[].problem` | ปัญหาที่พบและความเกี่ยวข้องกับคำถาม ไม่ใช่คำตำหนิทั่วไป |
| `issues[].evidence` | รายการ `source` และ `quote` ที่ตรวจย้อนกลับได้อย่างน้อยหนึ่งรายการ |
| `issues[].revision` | บอกว่าควรแก้อะไรตามหลักฐาน โดยยังไม่เขียนคำตอบใหม่ทั้งฉบับ |

แหล่งหลักฐาน `source` เลือกได้จาก `QUESTION`, P-ID ที่มีจริงของข้อนั้น เช่น `P1`, `DRAFT_ANALYSIS` หรือ `DRAFT_ANSWER` เท่านั้น P-ID อ้างถึง LAW_TEXT ของมาตรานั้น `quote` ต้องเป็นข้อความไม่ว่างที่คัดตรงจากแหล่งนั้นโดยไม่แปลหรือใส่จุดไข่ปลาแทนข้อความภายใน

- ข้ออ้างเกี่ยวกับกฎหมายต้องมีข้อความจาก P-ID ที่เกี่ยวข้อง การอ้างร่างซ้ำอย่างเดียวไม่ยืนยันว่ากฎถูก
- ข้ออ้างเกี่ยวกับข้อเท็จจริงหรือการละประเด็นต้องอ้างคำถามที่เกี่ยวข้อง
- ปัญหา analysis ขัดกับ answer อ้างข้อความจากร่างทั้งสองส่วนได้ โดยไม่อ้างว่าเพียงเท่านี้ตัดสินกฎหมายถูกผิดแล้ว
- ตรวจว่า quote มีอยู่จริงและ P-ID ถูกข้อแบบ deterministic ไม่ใช้ fuzzy matching เพื่อช่วย feedback ที่อ้างผิด การตรวจข้อความไม่ใช่การตรวจความหมายหรือการรับรองว่า feedback ถูกกฎหมาย
- schema, verdict, field และ quote ต้องผ่านครบก่อนนำ feedback ไปใช้ ถ้ามีรายการอ้างปลอม/ผิดแหล่ง ห้ามตัดทิ้งเฉพาะส่วนนั้นแล้วแอบใช้ส่วนที่เหลือ ให้เก็บร่างเดิมพร้อม `verifier_failed`
- ไม่ให้โมเดลส่ง overall verdict ซ้ำอีกฟิลด์หนึ่ง โปรแกรมตัดสินเส้นทางจากสี่แกนเพื่อลดผลที่ขัดกันเอง
- prompt จริงในขั้นถัดไปจะใช้ภาษาอังกฤษให้สอดคล้องกับ prompt ทดลองเดิม feedback บรรยายสั้นเป็นภาษาอังกฤษได้ แต่ quote คงข้อความต้นทาง ตัวอย่างภาษาไทยด้านล่างมีไว้ให้ผู้อ่านเอกสารเข้าใจ ไม่ใช่ few-shot example ที่จะใส่ใน prompt อัตโนมัติ

## 6. การเลือกเส้นทางและข้อกำหนด corrector

ตรวจเงื่อนไขตามลำดับในตาราง จากบนลงล่าง:

| เงื่อนไข | การดำเนินการ | สถานะที่บันทึก | คำตอบสุดท้าย |
|---|---|---|---|
| ไม่มีร่างสมบูรณ์จาก generation failure | ไม่เรียก verifier/corrector | `draft_failed` | ไม่มีคำตอบสำเร็จ |
| ID/context/provenance ขัดกัน หรือ input ใหญ่เกินงบที่รองรับ | หยุดก่อนเรียกขั้นที่มีปัญหา ตรวจข้อมูล/ทรัพยากร ไม่แปลงเป็นความผิดของโมเดล | `input_blocked` | ยังไม่ถือว่า Proposed ทำรายการนี้เสร็จ |
| Verifier เรียกไม่สำเร็จ, JSON/quote ไม่ผ่าน หรือข้อความถูกตัด | ไม่เรียก corrector ไม่ลอง verifier ซ้ำอัตโนมัติ | `verifier_failed` | ร่างเดิม |
| ผลตรวจใช้ได้และมี FAIL อย่างน้อยหนึ่งแกน แม้แกนอื่น UNCERTAIN | เรียก corrector หนึ่งครั้ง แก้เฉพาะปัญหาที่หลักฐานรองรับและรักษาความไม่แน่ใจส่วนที่เหลือ | `corrected` เมื่อได้คำตอบใช้ได้ | ฉบับที่ corrector ส่งกลับ |
| ผลตรวจใช้ได้ ไม่มี FAIL แต่มี UNCERTAIN | ไม่เรียก corrector | `kept_uncertain` | ร่างเดิม |
| ผลตรวจใช้ได้และ PASS ทั้งสี่แกน | ไม่เรียก corrector | `kept_pass` | ร่างเดิม |
| Corrector เรียกไม่สำเร็จ/JSON ไม่สมบูรณ์/schema หรือ citation enum ไม่ผ่าน | ไม่ลองซ้ำอัตโนมัติ | `correction_failed` | ร่างเดิม |

`input_blocked` เป็นปัญหาข้อมูลหรือทรัพยากรที่ยังต้องแก้ก่อนนับ run ว่าเสร็จ ไม่ใช่ PASS หรือ generation failure รายการที่ถูกบล็อกต้องปรากฏในสถานะรวม ไม่หายไปจากจำนวนข้อ

Corrector ต้อง:

1. อ่าน feedback เทียบกับคำถามและ context ก่อนแก้ ไม่ทำตามข้อเสนอที่ขัดหลักฐานโดยอัตโนมัติ หากไม่มีการแก้ที่รองรับได้ให้คืนร่างเดิมใน schema เดิมได้
2. แก้ส่วนที่สัมพันธ์กับปัญหาและส่วนที่ต้องเปลี่ยนตาม เช่น Application เปลี่ยนแล้ว Conclusion ต้องสอดคล้อง รักษาสาระที่มีหลักฐานรองรับอยู่แล้ว
3. ใช้ข้อมูลและ P-ID เดิม ไม่ค้นเพิ่ม ไม่เติมกฎหมายจากความจำ และไม่ใช้เฉลย
4. คืน JSON เดิมที่มีเพียง `analysis`, `answer`, `citation_ids`; answer เป็นภาษาไทยและใช้ข้อกำหนดความกระชับร่วมเดิม
5. ใช้ citation enum และ mapping เดิม การเก็บ ID ซ้ำครั้งแรกและบันทึก warning ยังคงตาม mapper เดิม ไม่เพิ่มนโยบายซ่อม citation เชิงความหมาย
6. จบหลังแก้หนึ่งครั้ง ไม่เรียก verifier อีกรอบ ไม่เลือกฉบับที่ดีกว่าโดยเปิดเฉลย และไม่ย้อนกลับเพราะคะแนนภายหลังลดลง

`corrected` หมายถึงขั้นแก้คืนคำตอบที่ใช้ได้ทางเทคนิค ไม่ได้หมายความว่าดีขึ้นจริง เก็บ `changed` แยกโดยเทียบเนื้อหาร่างกับฉบับแก้ ไม่ตีความว่าการเปลี่ยนถ้อยคำเท่ากับดีขึ้น กรณีเก็บร่างเดิมต้องรักษาค่าของคำตอบและ citation เดิมโดยไม่แปลหรือเรียบเรียงใหม่

## 7. งบ ทรัพยากร และเหตุผลของค่าที่เลือก

| รายการ | ค่าสำหรับเริ่มทดสอบ engineering | เหตุผล/ข้อจำกัด |
|---|---|---|
| ร่าง IRAC | ใช้ผลเดิม; งบเดิม 4,096 output tokens | แยกผลการตรวจแก้จากความต่างของการสุ่มร่างใหม่ |
| Verifier | เสนอเริ่มที่ 2,048 output tokens | ให้ feedback สั้นสี่แกน ไม่ต้องสร้างคำตอบเต็ม เป็นสมมติฐานด้านทรัพยากร ต้องตรวจว่าพอบน engineering |
| Corrector | 4,096 output tokens | คงเพดานคำตอบเต็มเทียบ baseline เดิม ไม่ใช่ค่าที่ paper ระบุว่าเหมาะที่สุด |
| การสุ่มและการรัน | temperature 0.0, seed 42, batch 1, หนึ่ง attempt ต่อขั้น และ SDK retry 0 | คงแนวทาง engineering เดิม ไม่รับประกันว่าจะได้คำตอบเหมือนกันทุกครั้ง |
| Context | Golden 16,384 / Retrieved 32,768 สำหรับเริ่มตรวจความเป็นไปได้ | ต้องตรวจขนาด prompt ของ Proposed เพิ่ม ไม่อนุมานว่าร่าง IRAC รันได้แล้ว Proposed จะพอ |
| จำนวนรอบแก้ | ไม่เกินหนึ่ง | จำกัดต้นทุนและให้วัดผลของการแก้ครั้งเดียวได้ชัด เป็นการตัดสินใจของเรา |

ก่อนเรียกแต่ละขั้นต้องตรวจคำสั่ง + context + ร่าง + feedback ที่เกี่ยวข้อง + พื้นที่ output โดยวิธีนับ tokens ที่เข้ากันได้กับโมเดล ไม่ใช้จำนวนอักษรเป็นหลักฐานว่าพอดี หากตรวจไม่ได้ต้องบันทึกข้อจำกัดและแก้การตรวจให้พร้อมก่อนรันเต็ม ห้ามให้ระบบตัด input/context เงียบ ๆ

เป้าหมาย final test ที่ใช้ 32k ร่วมกันยังอยู่ภายใต้การตรวจทรัพยากรตาม Protocol การเปลี่ยนงบหรือ prompt หลังพบปัญหา engineering ต้องออกเวอร์ชันและแยกผลใหม่ ไม่เพิ่มงบเฉพาะข้อที่ตอบผิดเพื่อให้ได้คำตอบสำเร็จมาปนกับรุ่นเดิม

## 8. ผลลัพธ์ การประเมิน และต้นทุน

### 8.1 ไฟล์ที่ตัวรันบันทึก

- `tax_response.json`: คำตอบสุดท้ายที่ใช้ได้ โดยรักษา interface เดิมทั้ง `model_content` และ `content` ที่แปลง citation เป็น law/section; ไม่เขียนทับผล IRAC baseline
- `tax_proposed_trace.json`: ข้อมูลประกอบการตรวจแก้และสถานะของทุก source ID รวมข้อที่ไม่มีคำตอบ เก็บแยกเพื่อไม่เพิ่ม verifier fields เข้า schema คำตอบ
- ไฟล์ Markdown ภาษาไทยที่อ่านได้ของคำตอบและ trace สร้างอัตโนมัติ โดยแสดงก่อน–หลัง ผลตรวจ หลักฐาน สถานะ และต้นทุน; การจัดรูปแบบไม่เปลี่ยนคำตอบที่โมเดลสร้าง

Trace ต้องมีอย่างน้อย: source/runtime ID, ชนิด context, ที่มาและ hash ของร่าง, context/P-ID map และ fingerprint ของ input, รุ่น prompt/config/model ที่ทราบ, ร่างเดิม, raw/parsed feedback, ผลตรวจรูปแบบ/quote, raw ผลแก้และฉบับแก้ถ้าใช้ได้, คำตอบสุดท้าย/แหล่งที่เลือก, สถานะ, `changed`, finish reason และต้นทุนแยกแต่ละขั้น

เก็บข้อมูลที่ไม่ทราบเป็น `null` พร้อมเหตุผล ไม่แทน usage/เวลาที่หายด้วย 0 การ resume ต้องตรวจ ID และ fingerprint ไม่ใช้จำนวนคำตอบอย่างเดียว และไม่เรียกขั้นที่มีการพยายามแล้วซ้ำอัตโนมัติหากสถานะกำกวมหลังโปรแกรมหยุด

### 8.2 ใช้คะแนน NitiBench เดิม

| คะแนนหลัก | วิธีใช้ |
|---|---|
| Coverage | 0/50/100 วัดความครอบคลุมสาระในเฉลย |
| Contradiction | 0/1 วัดความขัดแย้งกับเฉลยตามนิยาม benchmark |
| Citation Precision/Recall/F1 | เทียบชุด law/section กับชุดอ้างอิง; E2E F1 ในบริบทนี้คือ Citation F1 ไม่ใช่คะแนนใหม่อีกตัว |

“ก่อน” คือคำตอบ IRAC baseline ที่ใช้เป็นร่าง “หลัง” คือคำตอบสุดท้ายของ Proposed วัดด้วยเฉลยและ evaluator เดียวกันภายใน context เดียวกัน ทำภายหลังจากสร้างคำตอบครบได้ ไม่ส่งคะแนนเหล่านี้กลับเข้าการตรวจแก้

เปรียบเทียบก่อน–หลังสำหรับทุกข้อที่มีร่าง ไม่เลือกเฉพาะข้อที่สั่งแก้หรือข้อที่ดีขึ้น ส่วนข้อที่ไม่มีร่างยังอยู่ในตารางผลรวมและจำนวนความล้มเหลว แต่ไม่มีคู่คำตอบสำหรับวิเคราะห์การเปลี่ยนจาก correction

รายงานดีขึ้น/เท่าเดิม/แย่ลงแยกแต่ละคะแนน ไม่สร้างคะแนนรวมใหม่ ความขัดแย้งระหว่าง analysis กับ answer เป็นการวิเคราะห์แยกจาก Contradiction เทียบเฉลย ส่วน PASS/FAIL/UNCERTAIN และความผิดพลาดของ verifier เป็นข้อมูลประกอบ ไม่ใช่คะแนน benchmark

คำตอบที่หายและความล้มเหลวใช้กติกาใน Protocol ส่วน fallback ที่มีร่างเดิมใช้ประเมินคำตอบนั้นตามปกติและรายงานว่าขั้นตรวจ/แก้ล้มเหลว ห้ามนับ fallback เป็น PASS

### 8.3 ต้นทุนและขอบเขตข้อสรุป

- IRAC มีการสร้างคำตอบหนึ่งครั้ง Proposed ที่มีร่างสำเร็จมีร่าง + ตรวจ และเพิ่มการแก้เมื่อเข้าเงื่อนไข รวม 2–3 ครั้งในเชิงวิธี ไม่รวม evaluator
- เมื่อนำไฟล์ร่างเดิมมาใช้ แยกจำนวน calls ที่เรียกเพิ่มจริงออกจากต้นทุนเชิงวิธี ซึ่งยังต้องรวมต้นทุนสร้างร่างและ attempts ที่ล้มเหลว
- รายงาน calls, input/output tokens และเวลาแยกจากคะแนน ไม่มีการหัก F1 ด้วยจำนวน calls
- ถ้า Proposed ได้คะแนนดีขึ้น กล่าวได้ว่ากระบวนการทั้งชุดได้ผลต่างจาก IRAC ภายใต้การทดลองนี้ แต่ยังไม่แยกว่ามาจาก checklist IRAC โดยเฉพาะหรือจากโอกาสตรวจแก้เพิ่ม
- หากภายหลังเพิ่มการตรวจทั่วไปเป็น control ต้องใช้ร่าง/context เดียวกัน กติกาหลักฐานและเพดานรอบเหมือนกัน พร้อมรายงาน tokens/calls จริง ไม่อ้างว่าจำนวนรอบสูงสุดเท่ากันแปลว่าต้นทุนจริงเท่ากัน

## 10. จุดตรวจที่ใช้พัฒนาตัวรัน

ก่อนเรียกโมเดลจริง ให้สร้าง prompt verifier/corrector และตัวควบคุมขั้นตอน แล้วตรวจ offline ด้วยตัวอย่างสมมติครอบคลุมรายการต่อไปนี้:

| กรณี | ผลที่ต้องตรวจได้ |
|---|---|
| PASS ทั้งสี่แกน | ไม่เรียก corrector; คำตอบ/P-ID เดิมไม่เปลี่ยน |
| FAIL พร้อมหลักฐานถูกแหล่ง | เรียก corrector ครั้งเดียว แม้แกนอื่น UNCERTAIN |
| UNCERTAIN โดยไม่มี FAIL | เก็บร่างและสถานะไม่แน่ใจ ไม่รายงาน PASS |
| อ้าง quote ที่ไม่มีจริง หรือขาดแกนหนึ่ง | `verifier_failed`; เก็บร่างเดิม |
| Corrector ถูกตัด/JSON เสีย/ID นอก enum | `correction_failed`; เก็บร่างเดิม ไม่ซ่อมความหมายหรือเรียกซ้ำ |
| ไม่มีร่างสมบูรณ์ | `draft_failed`; ไม่เรียกโมเดลและยังมีรายการในสถานะรวม |
| Source/context/fingerprint ไม่ตรง หรือ input ไม่พอ | บล็อกก่อนเรียกขั้นที่มีปัญหา ไม่จับคู่โดยเดาหรือย่อ context |
| การสร้าง input และ resume | ไม่มีเฉลยรั่ว; รักษา Top 10/Golden/P-ID/schema; ไม่ทำขั้นเดิมซ้ำจากการนับแถว |

จากนั้นให้ผู้ใช้รัน pilot ของแต่ละ context ก่อน แล้วจึง engineering ครบชุด ตรวจการทำงานจริง ความยาวและความมีหลักฐานของ feedback รวมถึงความล้มเหลวก่อนตรึง ไม่ถือว่าต้องได้คะแนน Proposed สูงกว่า baseline จึงจะผ่านขั้นพัฒนา

ประวัติ: รุ่น 0.1 เพิ่มข้อกำหนดและเชื่อมแผนหลัก รุ่น 0.2 เพิ่ม prompt/schema และการตรวจ offline ตาม [PROPOSED_PROMPTS.md](PROPOSED_PROMPTS.md) รุ่น 0.3 เพิ่มตัวรัน/config และการตรวจงบ tokens ตาม [PROPOSED_RUNNER.md](PROPOSED_RUNNER.md) โดยยังไม่ได้เรียก Qwen, LLM ผู้ประเมิน หรือ live retrieval เพื่อตรวจผล Proposed จริง
