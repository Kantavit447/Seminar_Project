# ตรวจเส้นทางผล Proposed v6 หลังรันจริง

วันที่ตรวจ: 3 ตุลาคม 2026

## ผลที่ยืนยันได้

ตรวจผล Golden source 0036, 0041, 0008 โดยอ่าน trace, prompt/template, schema, OpenAIModel และ runner ที่ใช้จริง ตรวจซ้ำกับ schema แบบ offline โดยไม่เรียก LLM, Ollama หรือ retrieval และประกอบ prompt ของ Corrector ข้อ 0008 ซ้ำจาก input ที่บันทึกไว้ ไม่มีการเปลี่ยนผลทดลองหรือโค้ด

| source | feedback ของโมเดล | ตัวตรวจ/runner | ผลสุดท้าย |
| --- | --- | --- | --- |
| 0036 | PASS ทั้ง I/R/A/C แต่เหตุผลเขียนว่าคำตอบผิด | ผ่าน schema และการตรวจรูปแบบ; runner อ่าน verdict เป็น PASS | kept_pass, คำตอบ IRAC เดิม |
| 0041 | FAIL ทั้งสี่ด้าน แต่ลำดับ I,C,A,R และ ID หลักฐานซ้ำ | ผ่าน schema ระดับฟิลด์ แต่ไม่ผ่านการตรวจลำดับ I,R,A,C ใน runner; หากจัดลำดับใหม่อย่างเดียวก็ยังไม่ผ่านกติกา ID ซ้ำและจำนวน ID ในบางด้าน | verifier_failed, คำตอบ IRAC เดิม |
| 0008 | I=FAIL ทั้งที่เหตุผลบอกว่าร่างถูก; R/A/C=PASS | ผ่านรูปแบบและส่ง Corrector หนึ่งครั้ง | corrected แต่ changed=false: คำตอบเหมือนร่างทุกฟิลด์ |

คำว่า PASS/FAIL ในที่นี้คือ verdict ที่โมเดลส่ง ไม่ใช่คะแนน benchmark ไม่มีโค้ดแปลงเหตุผลภาษาเขียนเป็น verdict หรือเปลี่ยน verdict ให้เป็น PASS โดยอัตโนมัติ

## เส้นทางตั้งแต่ผลโมเดลถึงสถานะ

1. OpenAIModel เรียก `client.beta.chat.completions.parse(..., response_format=structure)` เมื่อมี schema ถ้า SDK ได้ `message.parsed` จะส่งค่าที่ model_dump แล้วกลับ runner; ถ้าไม่ได้ จะใช้ตัวแปลงข้อความของโมดูล ข้อมูลที่ trace เก็บเป็นผลหลังขั้น SDK/ตัวแปลงนี้ ไม่ใช่ raw HTTP bytes จึงไม่พิสูจน์ว่า backend บังคับ schema ได้เพียงใด
2. Runner เรียก `validate_verifier_feedback` ตรวจ Pydantic schema และกติกาข้ามฟิลด์ เช่น ลำดับ I/R/A/C, ID ไม่ซ้ำ, 1–3 ID ต่อด้าน, PASS อ้างประเภทหลักฐานครบ และ FAIL มี revision
3. หากตรวจผ่าน runner ใช้ค่า `verdict` โดยตรง หากมี FAIL จึงเรียก Corrector หากไม่มี FAIL เก็บร่างเดิม หากตรวจไม่ผ่านเก็บ `raw_feedback` และร่างเดิมพร้อม `verifier_failed`
4. Corrector ได้ feedback ที่ผ่านการตรวจแล้ว คำถาม กฎหมาย ร่างเดิม และ schema คำตอบเดิม ไม่ใช่ข้อมูลเฉลย

การแยกชั้นนี้สำคัญ: schema ที่รับ ID ถูกประเภทไม่สามารถรับรองได้ว่าข้อความที่ ID ชี้ไปสนับสนุนคำตัดสินจริง

## 0036: เหตุผลกับ PASS ขัดกัน

ด้าน I/R/A/C เป็น PASS ทั้งหมด แต่ reason ของแต่ละด้านระบุว่า answer สรุปว่าไม่ยกเว้นภาษีโดยไม่มีกฎหมายรองรับ ด้าน C ระบุชัดว่า answer ไม่ตาม analysis ข้อความเหล่านี้ขัดกับ PASS ในด้านเดียวกัน

ตรวจ schema ซ้ำแล้วผ่าน ไม่มีความผิดรูปแบบที่ตัวรับผลตรวจได้ ดังนั้น runner ทำงานตามกติกาที่กำหนด: เมื่อไม่พบ FAIL จึงเก็บร่างเดิมและไม่เรียก Corrector

หลักฐาน R/A ที่เลือกคือ P1-S2 ซึ่งเป็นเรื่องพืชผลทางการเกษตร ไม่ใช่บทอาหารสัตว์/การนำเข้าที่อยู่ P1-S4/P1-S7 ดังนั้นแม้โมเดลพูดว่ามีกฎหมายรองรับ ก็ไม่ได้แสดงหลักฐานที่รองรับจริง assessment บางช่องยาวถึงเพดาน 240 อักขระและตัดกลางความคิด เพิ่มความยากในการตรวจย้อนหลัง

**ข้อสรุป:** เป็นความไม่สอดคล้องใน feedback ของโมเดลและความผิดพลาดในการเลือกหลักฐานที่ปรากฏในผล ไม่พบว่าโค้ดสลับ verdict

## 0041: FAIL เกิด แต่ใช้ต่อไม่ได้

ลำดับด้านที่บันทึกคือ I,C,A,R ในขณะที่ contract ต้องเป็น I,R,A,C การตรวจ schema ระดับฟิลด์รับทั้งสี่ด้านได้ เพราะ `checks` เป็นรายการของชนิดทางเลือก; เงื่อนไขลำดับอยู่ใน validator หลังรับผล จึงรายงาน `Feedback must contain I, R, A, C exactly once, in order.`

ยังมีข้อผิดอื่นใน feedback เดียวกัน: A เลือก P1-S6 ทั้งในช่อง law และ supporting_ids; R ก็เลือก P1-S6 ซ้ำ ทำให้รายการแต่ละด้านมี ID ซ้ำ และด้าน A มี 4 ID เมื่อรวมทุกช่อง เกินเพดาน 3 แม้จัดลำดับใหม่โดยไม่แก้เนื้อหา ก็ยังใช้ feedback นี้ไม่ได้ การจัดลำดับให้อัตโนมัติจึงไม่ใช่การซ่อมทั้งหมด

P1-S6 เป็นข้อความเรื่องเงินได้ของบุตร/โบนัสผู้ถือหุ้น ไม่ใช่มาตรา 40(6) ที่ประเด็นนี้ต้องตรวจ ส่วนมาตรา 40(6) อยู่ P1-S10 จาก index เดียวกัน I/C/A/R ยังอ้าง DA-S1 เป็นหลัก แม้ Application/Conclusion อยู่ DA-S2

โมเดลแสดงความสงสัยในร่างเดิม แต่เหตุผล คำแนะนำ และหลักฐานยังไม่พอใช้เป็นการแก้ที่เชื่อถือได้ ระบบเก็บร่างเดิมอย่างถูกต้องตามกติกาการป้องกัน feedback เสีย และไม่มีการเรียก Corrector

**ข้อสรุป:** มีทั้งปัญหาการทำตามรูปแบบและคุณภาพหลักฐาน การเปลี่ยนตัวตรวจให้ยอมรับผลนี้ทันทีจะเปลี่ยนกติกาของการทดลอง

## 0008: Corrector ได้ข้อมูลครบและคืนร่างเดิม

I=FAIL แต่ reason บอกว่าร่างวิเคราะห์และตอบถูกตามกฎหมาย ส่วน R/A/C เป็น PASS คำแนะนำแก้ใน I ขอให้ระบุว่าดอกเบี้ยยังไม่จ่ายอาจรับเป็นรายจ่ายในรอบบัญชีที่เกิดภาระ ซึ่งเป็นใจความที่มีอยู่แล้วใน draft analysis และ final answer

ประกอบ prompt Corrector ซ้ำแบบ offline จากคำถาม กฎหมาย ร่าง และ feedback ใน trace พบว่ามี `[FEEDBACK_JSON]` ครบ, ร่างคำตอบครบ และ marker กฎหมาย P1-S3 อยู่ใน prompt คำสั่ง Corrector ระบุให้ตรวจ feedback กับต้นฉบับ และถ้าไม่จำเป็นต้องแก้ให้คืนร่างเดิม

ผลจริงของ Corrector เท่ากับร่างเดิมทุกฟิลด์: `analysis`, `answer`, `citation_ids` ใช้ 543 completion tokens และ 127.67 วินาที `status=corrected` ใน runner หมายถึง Corrector ส่งคำตอบที่ผ่านรูปแบบและการจับคู่ citation แล้ว ส่วน `changed=false` เป็นตัวบอกว่าเนื้อหาไม่เปลี่ยน ไม่มีคะแนนดีขึ้นจากการเรียกครั้งนี้

**ข้อสรุป:** การคืนร่างเดิมสอดคล้องกับคำสั่งที่ได้รับและไม่พบปัญหาการส่งข้อมูลไป Corrector แต่ไม่สามารถรู้เหตุผลภายในโมเดลแน่ชัดจาก output; ข้อมูลที่บันทึกสนับสนุนว่าการไม่แก้เป็นการตัดสินที่สมเหตุผลในกรณีนี้

## สิ่งที่ตรวจแล้วกับสิ่งที่ยังไม่ทราบ

ยืนยันได้:

- schema ของทั้งสามข้อรับโครงสร้างระดับฟิลด์ที่บันทึกได้; validator เพิ่มกติกาข้ามฟิลด์จึงปฏิเสธ 0041
- 0036 และ 0008 มีความขัดแย้งระหว่างเหตุผลกับ verdict จาก feedback ที่บันทึก; runner ไม่ได้สร้างความขัดแย้งนั้น
- 0041 มี ID ซ้ำและเลือกกฎหมายผิดช่วง นอกเหนือจากลำดับผิด
- 0008 ส่งข้อมูลที่ต้องใช้เข้า Corrector ตามการประกอบ prompt ซ้ำ และส่งร่างเดิมกลับจริง

ยังไม่ยืนยัน:

- backend Ollama หรือ SDK มีส่วนทำให้ลำดับ/ภาษาของผลออกมาเช่นนี้เพียงใด เพราะไม่มี raw HTTP payload ที่บันทึกในรอบที่ parse สำเร็จ
- การเปลี่ยน prompt/schema หรือใช้โมเดลอื่นจะแก้ความขัดแย้งด้านความหมายได้หรือไม่
- Corrector จะปรับคำตอบได้ดีเมื่อได้รับ FAIL ที่ถูกต้องและมีหลักฐานเหมาะสมหรือไม่; กรณีนี้มี FAIL ที่ไม่น่าเชื่อถือเพียงหนึ่งกรณีที่ผ่าน validator

## ข้อเสนอถัดไป

หยุดขยายการรัน v6 ในตอนนี้ เพราะสองในสามข้อที่ตั้งไว้ตรวจข้อผิดยังไม่ส่ง feedback ที่ใช้แก้ได้ และข้อที่เดิมถูกถูกส่งให้ Corrector โดยไม่จำเป็น

หากจะเดิน Proposed ต่อ ควรตัดสินเกณฑ์การยอมรับผลตรวจที่แยกสามเรื่อง: (1) รูปแบบถูก (2) เหตุผล/หลักฐานรองรับ verdict (3) การแก้ทำให้คำตอบดีขึ้น วัดกับ engineering ทุกข้อที่มีร่างครบและกรณีที่เดิมถูกด้วย ต้นทุนโมเดลต้องนับทั้ง Verifier และ Corrector ไม่ควรสร้างกฎจากคำว่า “incorrectly” เพื่อพลิก PASS เป็น FAIL เพราะจะทำให้ความหมายของผลและสถิติการทดลองเปลี่ยนอย่างไม่โปร่งใส

ก่อนทำ v7 ควรเลือกแนวทางที่เปลี่ยนเพียงจุดเดียวและตรวจ offline กับผล v6 ที่บันทึกไว้ รวมถึงกำหนดเพดานต้นทุน/จำนวนคำตอบที่จะรันจริง v6 ยังไม่ได้แสดงหลักฐานว่าแนวทางเพิ่มข้อความ assessment ช่วยคุณภาพการตรวจ แม้จะทำให้ข้อผิดเห็นชัดขึ้น
