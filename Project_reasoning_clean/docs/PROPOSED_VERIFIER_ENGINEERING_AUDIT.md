# ตรวจร่าง IRAC กับผล Verifier ในชุด engineering 10

วันที่ตรวจ: 3 ตุลาคม 2026

## ขอบเขตและวิธีอ่าน

ตรวจร่าง Golden IRAC ที่สร้างสำเร็จ **9 ข้อ** จาก `tax_response.json` เทียบกับ `reference_answer`, เฉลยฉบับเต็ม (`answer`), คำถาม และกฎหมาย Golden ที่บันทึกใน Clean Project แล้วเทียบผลตรวจของ Proposed v5 ทั้ง 9 ข้อและ v6 ที่รันจริง 3 ข้อ ไม่มีการเรียก LLM, retrieval หรือ evaluator เพิ่ม และไม่แก้ code, prompt หรือผลเดิม

นี่เป็น **การจัดกลุ่มแบบตรวจด้วยมือเพื่อวิเคราะห์ Verifier** ไม่ใช่คะแนน F1/Coverage/Citation ตาม NitiBench หรือคำวินิจฉัยกฎหมายปัจจุบัน ข้อที่ยังตีความได้หลายทางต้องให้ผู้วิจัยตรวจทานก่อนใช้เป็นผลทางการ

เกณฑ์จัดกลุ่ม:

- **ตรงใจความหลัก**: คำตอบตอบผลทางกฎหมายหลักตรงกับเฉลยและไม่พบข้อขัดกันสำคัญจากข้อมูลที่ตรวจ; ไม่ได้แปลว่าถ้อยคำและ analysis สมบูรณ์ทุกประโยค
- **บางส่วน/คลาดสาระสำคัญ**: ได้บางแกนของคำตอบ แต่ขาดเงื่อนไขหรือขั้นตอนที่เฉลยถือเป็นสาระสำคัญ หรือย้ายประเด็นจนผลไม่ครบ
- **ขัดกับเฉลย**: ข้อสรุปสำคัญตอบทิศทางตรงข้ามหรืออ้างผลอีกเรื่องแทนผลที่เฉลยกำหนด

สำหรับการดูความไวของ Verifier ให้ถือสองกลุ่มหลังเป็น **ร่างที่ควรทักท้วงอย่างน้อยหนึ่งประเด็น** คำว่า “ควรทักท้วง” ไม่ได้บังคับว่าทุกด้าน I/R/A/C ต้องเป็น FAIL หรือว่าข้อมูล Golden เพียงพอให้ Corrector เขียนเฉลยครบทุกข้อ

### จุดที่ควรตรวจทานโดยผู้วิจัย

- 0002: ถ้ารูปแบบคำตอบยอมให้ตัดขั้นตอนการยื่นรายการออกได้ อาจย้ายจาก “บางส่วน” เป็น “ตรงใจความหลัก” แต่ full answer ของ dataset ให้ทั้งออกหนังสือและยื่นรายการ
- 0003: ถ้าเกณฑ์นับเพียงอัตราหักภาษี อาจถือว่าใจความหลักตรง แต่คำถามและเฉลยระบุฐานเงินที่หักโดยเฉพาะ
- 0046: คำตอบใช้ถ้อยคำกำกวม จึงต้องดู rubric เรื่องการได้สาระของคำตอบ ไม่ควรแปลงเป็น “ขัดกับเฉลย” จากการไม่ใช้คำตรงกันอย่างเดียว
- 0008: ข้อสรุปหลักตรง แต่ส่วน R/A ใน analysis ใช้คำว่า “ยังไม่ได้รับชำระ” ขณะอธิบายรายจ่าย ควรตรวจเป็นความคลาดเคลื่อนระดับถ้อยคำ ไม่ใช้บังคับให้คำตอบหลักผิดโดยอัตโนมัติ

## ตัวเลขเชิงวินิจฉัยภายใต้เกณฑ์นี้

| รายการ | จำนวน |
| --- | ---: |
| IRAC Golden engineering ที่มีร่างสำเร็จ | 9 |
| ตรงใจความหลัก | 2 |
| บางส่วน/คลาดสาระสำคัญ | 3 |
| ขัดกับเฉลย | 4 |
| v5 ให้ PASS ทุกด้าน | 9 |
| ในกลุ่มขัดกับเฉลยชัด ๆ ที่ v5 ทักท้วง | **0/4** |
| หากนับกลุ่มบางส่วนด้วย ที่ v5 ทักท้วง | **0/7** |
| v5 เรียก Corrector | 0 |
| v5 คำตอบเปลี่ยนจาก IRAC | 0 |

ตัวเลข 0/4 และ 0/7 เป็น **ตัวชี้วัดการจับปัญหาตามการตรวจด้วยมือชุดเล็กนี้** ไม่ใช่ค่า recall ของ benchmark อย่างเป็นทางการ และตัวหาร 7 ขึ้นอยู่กับเกณฑ์ว่าสิ่งที่ขาดในกลุ่มบางส่วนถือเป็นข้อผิดที่ Verifier ควรตรวจพบหรือไม่ ไม่มีการใช้เฉลยเป็น input ของ Verifier

v6 ยังมีผลจริงเพียง 3 ข้อ (0036, 0041, 0008) จึงไม่สามารถให้คะแนนเทียบกับ v5 ทั้ง 9 ข้อแบบยุติธรรม ในสามข้อที่รัน: 0036 ยังปล่อยผ่านแม้ reason บอกว่าผิด; 0041 แสดง FAIL แต่ feedback ใช้ไม่ได้; 0008 กล่าวหาข้อที่ใจความหลักตรงว่า FAIL แล้ว Corrector คืนร่างเดิม ยังไม่มีการแก้ที่เปลี่ยนคำตอบและมีหลักฐานว่าดีขึ้น

## ต้นทุนที่บันทึกไว้

รวมจาก `usage.total_tokens` และ `llm_seconds` ใน trace ของแต่ละข้อ ไม่ใช่ราคาเงินหรือเวลาทั้งโปรแกรม:

| รอบ | ข้อที่รัน | tokens ที่บันทึก | เวลาเรียก LLM รวม |
| --- | ---: | ---: | ---: |
| v5 Golden | 9 | 55,516 | ประมาณ 12.9 นาที |
| v6 Golden pilot | 3 | 21,099 | ประมาณ 15.8 นาที |

v6 มี Verifier output ยาวขึ้นและข้อ 0008 เรียก Corrector เพิ่มหนึ่งครั้ง ตัวเลขสองแถวเป็นคนละจำนวนข้อ จึงห้ามนำยอดรวมมาเทียบว่า v6 ถูกหรือแพงกว่าต่อข้อโดยตรง และไม่ได้คิดต้นทุนการสร้าง IRAC ร่างเดิม

## ข้อสรุปเพื่อการตัดสินใจ

หลักฐานที่มี **ยังไม่แสดงประโยชน์ด้านคุณภาพคำตอบของ Proposed เวอร์ชันปัจจุบัน** v5 ใช้งานได้ทางโครงสร้างแต่ไม่ตรวจพบแม้สี่ข้อที่ร่างขัดกับเฉลยชัด v6 ทำให้เห็นปัญหาความสอดคล้องของเหตุผลกับ verdict มากขึ้น แต่ยังไม่มีการเปลี่ยนคำตอบที่ดีขึ้น และมี feedback ที่ใช้ไม่ได้

ควรหยุดเพิ่ม prompt ทีละเวอร์ชันโดยหวังให้ FAIL มากขึ้น ขั้นถัดไปที่มีเหตุผลคือเลือกเกณฑ์ตรวจคุณภาพ Verifier ล่วงหน้าและกำหนดงบการทดสอบ ก่อนทดลองวิธีใหม่เพียงหนึ่งการเปลี่ยนหรือเปรียบเทียบกับโมเดล verifier อื่น การตัดสินใจนั้นควรอิงทั้งข้อที่ผิดและข้อที่ถูกอยู่แล้ว รวมรูปแบบ feedback หลักฐาน และผลก่อน/หลังแก้ ไม่ใช้แค่จำนวน FAIL

ข้อมูลชุดนี้ยังเล็กและเป็น engineering ที่ใช้พัฒนา ไม่ควรสรุปผลไปยัง heldout หรือประชากรโจทย์ทั้งหมด ต้องเก็บรายงานนี้เป็นการวิเคราะห์ระหว่างพัฒนา และยืนยันการจัดกลุ่มด้วยผู้วิจัยก่อนอ้างเป็นตัวเลขหลัก
