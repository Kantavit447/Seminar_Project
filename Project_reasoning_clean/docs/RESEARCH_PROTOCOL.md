# แผนการทดลองหลัก: NitiBench / Thai Legal QA

รุ่นเอกสาร: 1.2 — 1 ตุลาคม 2026

สถานะ: แผนหลักสำหรับการพัฒนาและสร้างผลทดลอง ยังไม่ใช่การประกาศตรึง prompt หรือการตั้งค่าของ final test ทุกค่า

เอกสารนี้ใช้เป็นหลักสำหรับลำดับงานตั้งแต่วันนี้ ข้อความสถานะใน README และเอกสารการย้ายโปรเจกต์เก่าเป็นประวัติของช่วงนั้น หากพบความต่างให้ตรวจโค้ดและบันทึกการเปลี่ยนแปลงก่อนดำเนินงาน

## 1. ข้อตกลงล่าสุด

ผู้ใช้เลือกให้สร้างผลของทุกวิธีก่อน แล้วจึงพัฒนาและรัน evaluator ภายหลัง จึงใช้ลำดับงานดังนี้:

Protocol → CoT → IRAC → Proposed → ตรึงการสร้างคำตอบ → สร้างผล heldout ให้ครบ → เตรียมและตรึง evaluator → ประเมิน → วิเคราะห์และเขียนรายงาน

กำหนดนิยามคะแนนและกติกาการเปรียบเทียบไว้ในเอกสารนี้ตั้งแต่ต้น ส่วนโค้ด evaluator รุ่น LLM ผู้ประเมิน และงบ API เลื่อนไปเลือกภายหลังได้ ต้องเลือกและตรึงก่อนเริ่มให้คะแนน heldout และห้ามเลือกผู้ประเมินจากการที่ให้คะแนน Proposed สูงกว่า baseline

ผู้ใช้อนุญาตให้ใช้ LLM ภายนอกโดยกำหนดงบก่อนรัน ยังไม่มีเพดานเงินหรือการอนุญาตให้เรียก API ในรอบนี้ การรัน Qwen ยังเป็นหน้าที่ของผู้ใช้จนกว่าจะสั่งเปลี่ยนอย่างชัดเจน

## 2. เป้าหมายและคำถามวิจัย

ศึกษาผลของวิธีชี้นำ reasoning และการตรวจแก้คำตอบในงานกฎหมายภาษีไทย โดยตรึงโมเดลและหลักฐานที่แต่ละวิธีได้รับ

1. การเพิ่มคำสั่งให้วิเคราะห์เป็นลำดับช่วยเพิ่มคุณภาพจาก Direct ที่มีการวิเคราะห์สั้น ๆ หรือไม่?
2. โครงสร้าง IRAC ให้ผลต่างจากการชี้นำแบบ CoT ทั่วไปอย่างไร?
3. การตรวจร่าง IRAC และแก้เมื่อพบปัญหาช่วยหรือทำร้ายคำตอบในกรณีใด และใช้ต้นทุนเพิ่มเท่าไร?

เปรียบเทียบแต่ละวิธีภายใน context ประเภทเดียวกันก่อน การเปรียบเทียบข้าม Retrieved/Golden เป็นการวิเคราะห์เพิ่มเติม เพราะ context ต่างกันทั้งเนื้อหา จำนวนมาตรา และความยาว จึงไม่อ้างว่าส่วนต่างทั้งหมดเกิดจาก retrieval เพียงปัจจัยเดียว

## 4. สองประเภทของ context

### Saved Retrieved

ใช้ `results/current/retrieval_evaluation/section_based_no_ref/retrieval_results.json` เดิม รักษา Top 10, node IDs และลำดับเดิมในทุกวิธีของคำถามเดียวกัน อ่านข้อความจาก corpus เดิม ไม่มีการสร้าง embedding, index หรือเรียก live BGE-M3

### Golden

ใช้ `relevant_laws` เลือกข้อความจาก `chunking/golden/nodes.json` ด้วย exact resolver เดิม ไม่เพิ่ม fuzzy matching และไม่เรียก retriever เฉลยคำตอบและ reasoning อ้างอิงไม่ถูกส่งให้โมเดล

ทั้งสองแบบใช้ P-ID mapping, citation enum และ output schema เดิม รายการที่โมเดลเลือกถูกแปลงเป็น law/section แบบ deterministic ไม่มีการซ่อมความหมายของ citation ระหว่าง mapping

## 5. สี่วิธี รวมแปดเงื่อนไข

| วิธี | การดำเนินงาน | จำนวนเรียกโมเดลต่อข้อในเชิงวิธี |
|---|---|---:|
| Direct | ตอบพร้อมการวิเคราะห์สั้น ๆ ไม่มีโครงสร้างเฉพาะ | 1 |
| Zero-shot CoT แบบหนึ่งรอบ | เพิ่ม cue ให้คิดเป็นลำดับ ไม่มีตัวอย่าง | 1 |
| IRAC | จัดการวิเคราะห์เป็น Issue, Rule, Application, Conclusion | 1 |
| Proposed | สร้างร่าง IRAC → ตรวจ → แก้หนึ่งครั้งเมื่อพบปัญหา | 2–3 |

แต่ละวิธีใช้ทั้ง Retrieved และ Golden รวม 8 เงื่อนไข การนับต้นทุนจริงรวมทุก attempt และแยก API สำหรับผู้ประเมินออกจาก Qwen

### Direct

ใช้ prompt ปัจจุบันซึ่งมี `analysis` สั้น ๆ ชื่อในรายงานคือ Direct with brief unstructured analysis จึงไม่อธิบายว่าเป็นการตอบโดยไม่มี reasoning และไม่ใช่ No-RAG ผล engineering เดิมเก็บไว้ทั้งหมด

### Zero-shot CoT

ใช้ `reasoning_method: zero_shot_cot` เพิ่มเพียง `Let's think step by step.` หน้าคำสั่งใน user template ของ Direct ใช้ system prompt, context และ schema ร่วมกัน ไม่มีตัวอย่าง ไม่มี IRAC/checklist/verifier และเรียกโมเดลหนึ่งรอบเพื่อคืน analysis/answer/citation_ids พร้อมกัน

ระบุในรายงานว่าเป็นการดัดแปลง Zero-shot CoT เป็นแบบหนึ่งรอบ ต้นฉบับ Kojima ใช้สองขั้นตอนสำหรับสร้าง reasoning และสกัดคำตอบ ไม่อ้างว่าเรา reproduce ขั้นตอนของต้นฉบับทั้งหมด

### IRAC

เปลี่ยนเฉพาะคำชี้นำวิธีวิเคราะห์เป็น I/R/A/C โดยคงข้อกำหนดหลักฐาน ภาษา และ interface ร่วมกัน การแบ่งหัวข้อไม่ใช่หลักฐานโดยตัวมันเองว่า reasoning ถูกต้อง

ใช้ Zero-shot IRAC prompting ที่ดัดแปลงจาก Yu et al. (2022) เรียกโมเดลหนึ่งรอบ ไม่มีตัวอย่าง แบ่งสี่หัวข้อภายใน `analysis` เดิม ระยะ engineering คง Golden 16k / Saved Retrieved 32k ตาม Direct และ CoT รายละเอียด prompt, config และวิธีตรวจอยู่ใน [IRAC.md](IRAC.md)

### Proposed

ข้อกำหนดสำหรับพัฒนาอยู่ใน [PROPOSED_DESIGN.md](PROPOSED_DESIGN.md): ที่มาจากงานวิจัย, rubric I/R/A/C, รูปแบบ feedback, การเลือกเส้นทาง, การเก็บร่างเมื่อขั้นตอนล้มเหลว และการเก็บก่อน–หลัง มี prompt/schema/ตัวประกอบข้อความที่ผ่าน offline แล้วตาม [PROPOSED_PROMPTS.md](PROPOSED_PROMPTS.md) ยังไม่มี runner ครบขั้นตอน และยังไม่ตรึง prompt ของ final test

ใช้ร่างจาก IRAC baseline ของข้อและ context เดียวกันเป็น input ตรวจสี่แกน:

| แกน | สิ่งที่เปรียบเทียบ |
|---|---|
| I — Issue alignment | ประเด็นในร่างตรงและครอบคลุมคำถาม |
| R — Rule grounding | กฎในร่างรองรับด้วย context และรักษาเงื่อนไข/ข้อยกเว้น |
| A — Application consistency | ปรับใช้กฎกับข้อเท็จจริงโดยไม่เพิ่มข้อเท็จจริงเอง |
| C — Conclusion consistency | ข้อสรุปตามจากการปรับใช้และตอบประเด็น |

ผลตรวจแต่ละแกนเป็น PASS/FAIL/UNCERTAIN หาก PASS ทั้งหมดใช้ร่างเดิม หากมี FAIL พร้อมหลักฐานที่ผ่านการตรวจรูปแบบและข้อความอ้างอิงให้ corrector แก้ครั้งเดียวแล้วจบ ไม่วนจน PASS หากไม่มี FAIL แต่มี UNCERTAIN ให้เก็บร่างพร้อมสถานะไม่แน่ใจ ทุกบทบาทใช้ Qwen ตัวเดียวกันและ context เดิม ไม่มีการเห็นเฉลย คะแนนประเมิน หรือค้นกฎหมายเพิ่ม

หากข้อมูลไม่พอ ให้รายงานข้อจำกัดของหลักฐาน ห้ามเติมข้อเท็จจริงหรือกฎหมายจากความจำเพื่อให้ดูเหมือนแก้สำเร็จ หาก verifier/corrector ล้มเหลวทางเทคนิค ให้เก็บร่าง IRAC เป็น final พร้อมสถานะล้มเหลว ไม่บันทึกว่าเป็น PASS ต้องตรวจเส้นทางนี้ก่อนตรึง implementation

แม้นำร่าง IRAC กลับมาใช้ในการทดลอง ก็ต้องนับต้นทุนสร้างร่างในต้นทุนเชิงวิธีของ Proposed เก็บ pre/post, verdict, feedback และต้นทุนแยกรายขั้นใน artifact ประกอบ โดยรักษา schema คำตอบสุดท้าย

กรณี IRAC ไม่มีร่างสมบูรณ์ให้บันทึก draft_failed ไม่สร้างร่างใหม่เงียบ ๆ และยังนับอยู่ในผลรวม ส่วน input/context ที่ไม่ตรงหรือขนาดเกินงบเป็น input_blocked ที่ยังต้องแก้ก่อนนับว่ารันเสร็จ การทดลองตัวตรวจทั่วไปเป็นงานเสริมที่ยังไม่เพิ่มใน 4 วิธีหลัก

## 6. ค่าควบคุมและสถานะ context window

- ใช้น้ำหนัก Qwen และ quantization เดียวกัน ตรวจ digest ก่อน final test
- `temperature: 0.0`, `seed: 42`, `batch_size: 1`
- Generator ใช้ `max_tokens: 4096` ตาม Direct เดิม ข้อเสนอเริ่มทดสอบ Proposed คือ verifier 2,048 และ corrector 4,096 output tokens เป็นค่าทางวิศวกรรมที่ยังต้องตรวจบน engineering ก่อนตรึง ไม่ใช่ค่าที่งานวิจัยกำหนด
- `answer` ภาษาไทย; ระยะเริ่ม CoT คงคำสั่ง `analysis` ภาษาอังกฤษและความกระชับตาม Direct เดิม รายงานกรณีไม่ทำตามภาษา ไม่แก้คำตอบที่สร้างแล้วหรือเรียกซ้ำเพียงเพราะภาษา
- ไม่มีการส่งเฉลย reference answer หรือคะแนนให้ generation ทุกขั้น
- Citation interface และ context format เดียวกันทุกวิธี

Engineering Direct เดิมใช้ Golden 16k และ Retrieved 32k จึงสร้าง CoT engineering ด้วยค่าเดียวกันต่อ context เพื่อเปรียบเทียบผลของ cue โดยไม่เปลี่ยนค่ารันพร้อมกัน

เป้าหมายสำหรับ final test คือ 32k ร่วมกันทั้งสอง context แต่ยังไม่ถือว่าผ่านการทดสอบ ต้องตรวจขนาด prompt + ร่าง + feedback + พื้นที่ output และทรัพยากรเครื่องก่อนตรึง ไม่ตัด context เงียบ ๆ หากเปลี่ยนค่ารัน ต้องตรวจ engineering ของเงื่อนไขที่เกี่ยวข้องและแยกผลตามรุ่น ไม่ปนผล Golden 16k กับ 32k เป็นเงื่อนไขเดียวกัน

การตรวจ heldout เพื่อเตรียมรันก่อน generation จำกัดที่โครงสร้าง ID การมีอยู่ของ node และขนาด input ไม่ใช้เฉลยหรือคุณภาพคำตอบเพื่อปรับวิธี

## 7. นิยามการประเมินที่กำหนดไว้ล่วงหน้า

| ด้าน | เกณฑ์ |
|---|---|
| Coverage | ความครอบคลุมสาระจำเป็นของเฉลย: 0, 50, 100 |
| Contradiction | ความขัดแย้งของคำตอบกับเฉลยตามนิยาม NitiBench: 0 หรือ 1 |
| Citation | Precision, Recall, F1 ของชุด law/section เทียบชุดอ้างอิง |
| Correction | การเปลี่ยน Coverage/Contradiction/Citation ก่อน–หลังรายข้อ พร้อมดีขึ้น/เท่าเดิม/แย่ลงแยกแต่ละมิติ |
| Verifier | สัดส่วน PASS/FAIL/UNCERTAIN/correction และการวิเคราะห์การตรวจพลาดจากตัวอย่างที่ตรวจด้วยคน เป็นข้อมูลประกอบ ไม่ใช่คะแนน benchmark |
| ต้นทุน | Calls, input/output tokens, เวลา และความล้มเหลวทุกขั้น |

ไม่รวมคะแนนเป็นคะแนนเดียวโดยเพิ่มน้ำหนักหลังเห็นผล หาก Coverage เพิ่มแต่ Contradiction แย่ลง ต้องรายงานทั้งสองด้าน

E2E F1 ในบริบทนี้คือ Citation F1 ไม่ใช่คะแนนคำตอบอีกตัว การวัดก่อน–หลังใช้คะแนนเดิมเปรียบเทียบร่าง IRAC กับคำตอบสุดท้ายของ Proposed ภายในข้อและ context เดียวกัน รวมข้อที่เก็บร่างเดิมด้วย ทำภายหลังสร้างผลครบได้โดยไม่ส่งคะแนนให้ verifier/corrector ความขัดแย้งภายในเหตุผล/คำตอบตรวจเป็นการวิเคราะห์แยก ไม่ปนในคะแนน Contradiction เทียบเฉลย

Citation จับคู่ผ่าน source_idx และใช้ TP = predicted ∩ reference, FP = predicted − reference, FN = reference − predicted สูตรใน `script/metric_e2e.py` ของต้นทางมี FP/FN สลับ จึงไม่คัดลอกมาใช้โดยไม่ตรวจ เลือกกติกา normalization และรายงาน micro/macro ให้ชัดก่อนให้คะแนน final test

Golden ที่อนุญาต citation จากชุดเฉลยเท่านั้นอาจได้ precision = 1 สำหรับชุดไม่ว่างโดยข้อจำกัดของ interface จึงต้องแยกการเลือก ID ถูกชุดจากการใช้กฎหมายสนับสนุนคำตอบได้จริง

ผู้ประเมินคำตอบเห็นคำถาม เฉลย และคำตอบสุดท้าย โดยไม่เห็นชื่อวิธีหรือ verdict ของ verifier ไม่ใช้ analysis ที่ยาวกว่าเป็นเหตุให้ได้คะแนนคำตอบดีกว่า การตรวจ analysis และการรองรับข้ออ้างด้วย citation ทำเป็นการวิเคราะห์แยก

## 8. เตรียม evaluator หลังสร้างผลครบ

เริ่มจากกรอบประเมินของ NitiBench ซึ่งรายงานการใช้ `gpt-4o-2024-08-06` เป็นข้อมูลอ้างอิง ยังไม่เลือก API รุ่นนั้นโดยอัตโนมัติ ต้องตรวจความพร้อม ราคา และงบเมื่อถึงรอบประเมิน

1. สร้างและตรวจโค้ดคะแนนกับตัวอย่างที่รู้คำตอบ รวมกรณี citation เกิน/ขาด และ schema ผิด
2. ใช้ engineering เท่านั้นในการปรับ rubric/prompt และเทียบคะแนนกับคน
3. บันทึกรุ่นผู้ประเมิน พารามิเตอร์ prompt hash และเพดานงบก่อนเรียก API
4. ตรึง evaluator ก่อนเริ่มให้คะแนน heldout และใช้เหมือนกันทั้ง 8 เงื่อนไข
5. ตรวจโดยคนอย่างน้อย 20% ของ 320 คำตอบ: เลือก 8 source IDs จาก 40 ด้วย seed ที่บันทึกไว้ แล้วตรวจครบ 8 เงื่อนไขแบบปิดชื่อวิธี รวม 64 รายการ เพิ่มกรณี correction ที่สำคัญโดยระบุว่าเป็นการวิเคราะห์เพิ่มเติม

ห้ามปรับผู้ประเมินจากผลที่ทำให้ Proposed ดูดีขึ้น หากพบข้อผิดพลาดของ evaluator หลังเริ่มให้คะแนน ต้องบันทึกและประเมินใหม่ทุกผลที่ได้รับผลกระทบอย่างสม่ำเสมอ

## 9. ความล้มเหลวและการทำซ้ำ

ระยะ engineering ใช้หนึ่ง attempt ต่อ generation stage ตาม `diagnostic.max_retries: 1` และ SDK retry = 0 เดิม บันทึกทุกกรณีที่รันใหม่ด้วยเหตุผล ไม่เลือกคำตอบดีที่สุดจากหลายครั้ง

เมื่อไม่มีคำตอบที่ใช้ได้ ให้รายงาน generation failure, Coverage = 0 และ citation เป็นชุดว่างสำหรับการคำนวณด้านนั้น ส่วน Contradiction ให้เป็นสถานะประเมินไม่ได้และแสดงจำนวนคำตอบที่ประเมินได้กับ completion rate เสมอ ไม่ทำให้คำตอบที่หายไปกลายเป็น no-contradiction หากเป็นความล้มเหลวของผู้ประเมิน ให้แยกจาก generation failure และแก้การประเมินตามกติกาเดียวกัน ไม่แทนด้วยคะแนนเริ่มต้นเงียบ ๆ

ก่อน final test ต้องตรวจ resume ด้วย source_idx และ fingerprint ของ config/prompt เพื่อไม่ผสมผลต่างเวอร์ชัน ค่าเริ่มต้นของ runner ยัง resume ตามจำนวนรายการ ส่วนตัวเลือก `--continue-on-length-failure` ที่เพิ่มวันที่ 1 ต.ค. 2026 ตรวจ runtime/source ID และหลักฐาน length failure เพื่อทำเฉพาะข้อค้างใน engineering โดยคงหนึ่ง attempt ต่อข้อ รายละเอียดอยู่ใน [รายงานการรันต่อ](GOLDEN_IRAC_ENGINEERING_FAILURE_0001.md) การตรวจ fingerprint ครบชุดยังต้องทำก่อน final test และยังต้องแยกโฟลเดอร์ผลแต่ละวิธี/รุ่น

บันทึก raw response, usage, เวลา, finish reason และสถานะการตัดข้อความให้เพียงพอก่อน final test ไม่ถือว่า `temperature=0` และ seed รับประกันผลเหมือนเดิมทุกเครื่อง

ก่อนแต่ละวิธีรัน: ตรวจ prompt offline → ทดสอบหนึ่งข้อโดยผู้ใช้ → engineering ครบ 10 ทั้งสอง context → ตรวจความสมบูรณ์ ไม่เรียกรันโมเดลโดยผู้ช่วยอัตโนมัติ

## 11. สิ่งที่ถือว่างานเสร็จ

มี implementation/configs ของ 8 เงื่อนไข ผลดิบและบันทึกที่ตรวจย้อนกลับได้ เกณฑ์และผลประเมิน ตารางคุณภาพและต้นทุน การวิเคราะห์ correction และรายงานตอบคำถามวิจัยทั้งสามข้อ ผลที่ Proposed ไม่ช่วยหรือทำให้แย่ลงเป็นผลที่รายงานได้ ไม่ต้องเพิ่มวิธีเพื่อให้ได้ผู้ชนะตามคาด

รายงานเปรียบเทียบรายคำถามและความไม่แน่นอนแยกแต่ละ context ไม่ถือว่าผล 320 รายการเป็นคำถามอิสระ 320 ข้อ ข้อสรุปจำกัดกับโมเดลและชุดทดสอบนี้

## 12. งานวิจัยอ้างอิงและบทบาท

- [NitiBench](https://arxiv.org/abs/2502.10868): dataset และกรอบประเมิน
- [Kojima et al.](https://arxiv.org/abs/2205.11916): แนวคิด Zero-shot CoT ซึ่งเราดัดแปลงเป็นหนึ่งรอบ
- [Legal Prompting](https://arxiv.org/abs/2212.01326): เหตุผลของการทดลองโครงสร้างทางกฎหมาย ไม่ใช่หลักฐานว่า IRAC ดีที่สุดเสมอ
- [Chain of Logic](https://arxiv.org/abs/2402.10400): เหตุผลของการตรวจองค์ประกอบและความสัมพันธ์ของเงื่อนไข ยังไม่ใช่วิธีทดลองหลัก
- [LegalReasoner](https://arxiv.org/abs/2506.07443): แรงบันดาลใจด้าน verification/correction เราไม่ได้จำลองระบบฝึก verifier และเครื่องมือของต้นฉบับ
- [Self-Refine](https://arxiv.org/abs/2303.17651): อ้างอิงเสริมสำหรับวงจรร่าง → feedback เฉพาะเจาะจง → แก้ ด้วยโมเดลตัวเดิม เราดัดแปลงเป็นการตรวจตาม IRAC และแก้ได้ครั้งเดียว
- [Huang et al.](https://arxiv.org/abs/2310.01798): เหตุผลที่ต้องวัดความเสียหายจาก correction และต้นทุนอย่างเป็นธรรม
