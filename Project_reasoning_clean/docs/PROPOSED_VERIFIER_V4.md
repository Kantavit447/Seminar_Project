# Proposed v4: ให้โมเดลเลือกหมายเลขหลักฐาน

## เหตุผลและขอบเขต

v3 เขียนจบใน pilot สองข้อ แต่แก้/แปลข้อความภายใน quote จึงไม่ผ่านการตรวจคัดตรง รุ่น 4 เปลี่ยนการระบุหลักฐานเป็นการเลือก `evidence_ids` โปรแกรมดึงข้อความต้นฉบับเอง การเลือกหมายเลขที่มีจริงไม่ได้แปลว่าเลือกหลักฐานที่เกี่ยวข้องหรือตัดสินกฎหมายถูกต้อง ยังต้องตรวจความหมายและประเมินผลตาม benchmark ภายหลัง

นี่เป็นการปรับระบบของโครงการเพื่อแก้ปัญหาที่พบใน engineering ไม่ใช่การทำซ้ำรูปแบบของงานวิจัยต้นแบบ ไม่มีเฉลยหรือรายละเอียดเฉพาะคำตอบ pilot ใน prompt และไม่ใช้ heldout ปรับวิธี

## หมายเลขและข้อความ

| หมายเลข | แหล่ง |
|---|---|
| Q-S1, Q-S2 | คำถาม |
| DA-S1, DA-S2 | analysis ของร่าง IRAC |
| DR-S1, DR-S2 | answer ของร่าง IRAC |
| P1-S1, P1-S2 | LAW_TEXT ของกฎหมาย P1 |

หมายเลขมีขอบเขตเฉพาะข้อ ต้องตีความคู่กับ source_idx และชนิด context ส่วน citation ในคำตอบยังเป็น P1, P2 ตาม enum เดิม ไม่ใช้ P1-S1 เป็น citation

โปรแกรมแบ่งเป็นช่วงข้อความโดยตั้งเป้าราว 600 ตัวอักษร ใช้บรรทัดหรือช่องว่างที่มีอยู่ก่อน หากไม่พบจะเก็บช่วงยาวขึ้นแทนตัดกลางคำ เก็บ `start`/`end` เป็นตำแหน่งตัวอักษร Python พร้อมข้อความต้นฉบับ การแบ่งนี้ไม่ใช่การตัดสินขอบเขตประโยคหรือเงื่อนไขกฎหมาย

ทั้ง verifier และ corrector เห็นทุกช่วงของคำถาม กฎหมาย และร่างครบตามลำดับเดิม พร้อม marker หมายเลข ไม่มีการตัด context/เลือกเฉพาะหลักฐานบางส่วนเข้ามา ให้โมเดลอ่านช่วงข้างเคียงด้วยเพื่อรักษาเงื่อนไขและข้อยกเว้น เมื่อเอาข้อความของแต่ละช่วงมาต่อกันต้องตรงต้นฉบับทุกตัวอักษร P-ID และลำดับมาตรายังเดิม

## Feedback และการตรวจ

แต่ละแกนมี `axis`, `verdict`, `reason`, `evidence_ids`, `revision` เลือกหลักฐาน 1–3 หมายเลขที่ไม่ซ้ำ ไม่มี quote/รายการปัญหาซ้อน โมเดลได้รับ enum ของหลักฐานที่มีจริงในข้อนั้น โปรแกรมยังตรวจ source ที่จำเป็นสำหรับ PASS และตรวจว่า PASS/UNCERTAIN มี revision เป็น null ส่วน FAIL มีคำแนะนำแก้

corrector ได้ feedback ที่มี ID และ context แบบติดหมายเลขเดียวกับ verifier เลือกแก้เมื่อ feedback ใช้ได้และมี FAIL เท่านั้น ชุดหลักฐานที่ดึงกลับในรายงานเป็นการแสดงข้อความเดิม ไม่ใช่การซ่อมคำตัดสินของ verifier

ตัวรันเก็บ `evidence_index` และ `resolved_evidence` ใน trace ของข้อที่ผ่าน validation รวมทั้งแสดงหลักฐานต้นฉบับใน Markdown เฉพาะผล Proposed แยกจาก schema คำตอบหลัก เพิ่ม hash ของโค้ดสร้างหลักฐานและ prompt builder ใน fingerprint ของ v4 เพื่อบล็อก resume หากวิธีสร้าง ID เปลี่ยน

## การทดลอง

ใช้ร่าง IRAC เดิม งบ verifier 2,048/corrector 4,096 และ context window เดิม config/output แยกเป็น v4 ข้อมูลเพิ่มจาก marker และ enum ต้องถูกนับใน input budget ใหม่ หากเกินโปรแกรมจะบล็อกก่อนเรียกโมเดล

เริ่มลองข้อสั้นที่เคยทดสอบ จาก `C:\NitiBench\Project_reasoning_clean`:

```powershell
.\.venv\Scripts\python.exe -B -m script.response_proposed --config-path config/local/response/proposed_golden_v4_engineering_10.yaml --source-idx 0003
```

ผลอยู่ใน `results/current/common_interface_v3/golden_proposed_v4_engineering_10_ctx16384/diagnostics/source_0003/` หากผ่านให้ตรวจว่าหลักฐานที่เลือกเกี่ยวข้องและเหตุผลรองรับ verdict ก่อนลองข้อยาว ไม่ถือว่า JSON ผ่านแล้วเท่ากับคำตอบถูกต้อง

การตรวจ offline อยู่ใน `tools/validation/validate_proposed_v4_offline.py` ผ่านกับร่าง 19 รายการ ตรวจข้อความครบและตำแหน่งต้นฉบับ การดึง ID กลับ และปฏิเสธข้อมูลผิดกติกา 133 กรณี รวมถึงทดสอบเส้นทาง PASS/UNCERTAIN/FAIL/feedback ผิดและ resume ในทั้งสอง context ด้วยโมเดลจำลอง ไม่มีการเรียก Qwen หรือ live retrieval

การประมาณงบรวมสูงสุดของ verifier คือ Golden 13,202/16,384 และ Saved Retrieved 26,317/32,768 tokens; corrector เมื่อใช้ feedback สมมติคือ 15,271 และ 28,147 ตามลำดับ รวมพื้นที่ output และ margin แล้ว ต้องตรวจอีกครั้งกับ feedback จริงก่อนเรียก corrector ชุดทดสอบ v3 ยังผ่าน และ hash ของ prompt/ผลเก่า 24 ไฟล์ตรงกับก่อนแก้ การผ่าน offline ยังไม่ใช่หลักฐานว่า verifier เลือกหลักฐานหรือตัดสินถูกในงานจริง
