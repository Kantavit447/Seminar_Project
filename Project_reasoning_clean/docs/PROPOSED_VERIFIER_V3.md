# Verifier รุ่น 3: ลดข้อมูลซ้ำใน feedback

รุ่น 2 ของ pilot Golden source `0000` ถูกตัดเมื่อใช้ output ครบ 2,048 tokens ข้อความก่อนถูกตัดมีหลักฐานยาวซ้ำทั้งระดับแกนและระดับปัญหา ให้ PASS พร้อมรายการข้อผิดพลาด และอ้างข้อความต่างมาตราเป็น P-ID เดียวกัน จึงไม่ใช่ปัญหาความยาวอย่างเดียว และยังนำข้อความนั้นไปให้ corrector ไม่ได้

## รูปแบบใหม่

แต่ละแกน I/R/A/C มีเพียง `axis`, `verdict`, `reason`, `evidence`, `revision` ยกเลิกรายการ `issues` ที่ซ้อนอยู่ภายใน หลักฐานเก็บครั้งเดียวต่อแกน 1–3 ชิ้น คัดตรงชิ้นละไม่เกิน 80 ตัวอักษร เหตุผลไม่เกิน 200 ตัวอักษร และคำแนะนำแก้ไม่เกิน 160 ตัวอักษร ให้เลือกปัญหาสำคัญที่สุดของแกน ไม่เขียนรายการปัญหาย่อยซ้ำ

PASS/UNCERTAIN ต้องมี `revision: null` ส่วน FAIL ต้องมีคำแนะนำแก้ที่ไม่ว่าง โปรแกรมปฏิเสธผลที่ผิดกติกา ไม่เปลี่ยน PASS เป็น FAIL ให้เอง และไม่ใช้ JSON ที่ถูกตัด

PASS ยังคงต้องชี้แหล่งหลักฐานตามรุ่น 2: I=คำถาม+ร่าง, R=กฎหมาย+ร่าง, A=คำถาม+กฎหมาย+ร่าง, C=analysis+answer ส่วน quote ของทุก verdict ต้องตรงข้อความจากแหล่งที่ประกาศ P-ID อ้างเฉพาะ LAW_TEXT ไม่ใช่หัวมาตราหรือข้อความของมาตราอื่น

ข้อจำกัดความยาวเป็นค่าทดลองเพื่อให้ feedback กระชับบนโมเดล 7B ไม่ใช่ค่าที่คัดลอกจากงานวิจัย และอาจทำให้รายงานปัญหาได้ไม่ครบ จึงต้องตรวจคุณภาพหลัง pilot การคัด quote ถูกไม่ได้รับรองการตีความกฎหมายหรือ verdict ถูกต้อง

## สิ่งที่ใช้ต่อ

ใช้ร่าง IRAC, context, P-ID, corrector prompt และ schema คำตอบเดิม corrector อ่านเหตุผลและคำแนะนำจาก feedback ใหม่ งบ verifier 2,048/corrector 4,096 ยังเท่าเดิมเพื่อทดลองผลของการลดความซับซ้อนก่อน เพิ่ม config/output รุ่น 3 แยกจากรุ่น 1–2 โดย config เก่ายังเลือก schema/prompt เก่าได้ ไม่จำเป็นต้องสร้างร่าง IRAC ใหม่

## ผลตรวจ offline

ชุดตรวจ `tools/validation/validate_proposed_v3_offline.py` ผ่านกับร่าง 19 รายการ ปฏิเสธข้อมูลผิดกติกา 133 กรณี และทดสอบ PASS, UNCERTAIN, FAIL→corrector, feedback ผิดรูปแบบ และ resume ด้วยโมเดลจำลองในทั้งสอง context งบ verifier และ corrector ที่ใช้ feedback สมมติสั้นผ่านทั้ง 19 รายการ; ต้องตรวจงบ corrector อีกครั้งหลังได้ feedback จริง

ชุดทดสอบ v2 ยังผ่าน รวมการตรวจ schema เดิมของ v1 ไฟล์ prompt/ผลเก่า 13 ไฟล์ตรงกับ hash ก่อนแก้ ไม่มีการเรียก Qwen หรือ live retrieval การผ่าน offline รับรองการทำงานของโปรแกรมกับข้อมูลทดสอบ ไม่รับรองว่าโมเดลจะสร้าง feedback ถูกต้องหรือจบภายในงบจริง
